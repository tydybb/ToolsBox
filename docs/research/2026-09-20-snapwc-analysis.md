# SnapWC 2.2.2 视频识别与下载机制分析

分析日期：2026-09-20。结论基于用户提供的 ZIP 静态源码和官网说明，不代表已安装插件实测成功率。

## 结论

SnapWC 的主要优势是“网络请求嗅探 + 站点专用规则 + 流媒体清单解析”，而不是把网页中的 `blob:` 地址直接转换成下载地址，也不是一个保证所有网站都能下载的解密工具。

对宝哥工具箱最值得借鉴的是资源发现和分类层。最终下载仍应保留现有 yt-dlp / FFmpeg 处理、音视频配对、时长与轨道完整性校验，不能照搬插件的分片拼接逻辑。

## 2. 视频如何被发现

### 网络层是主要入口

`background.js` 中 `Vt.init → sp` 注册了以下监听：

1. `webRequest.onSendHeaders`：记录请求 ID、时间和请求头。
2. `webRequest.onResponseStarted`：读取响应 URL、类型、响应头等信息并分类。
3. `webRequest.onCompleted`：对尚未处理的请求补处理，避免重复计入。

因此，即使播放器的 `video.src` 是 `blob:`，只要底层仍请求 HTTP(S) 媒体、清单或轨道，插件就可能捕获到这些实际地址。这里不是下载 `blob:` 本身，也没有证据表明它通用劫持所有网站的 MSE 缓冲区。

### 不只依赖文件后缀

`rp / cp / up / Qn` 综合处理：

- URL 后缀和 `Content-Type`；
- `Content-Length`；
- `Content-Range` 中的总大小，而不只把本次 Range 响应大小当文件大小；
- 请求类型及站点专用规则；
- 流媒体清单的类型、清晰度、轨道和分片信息。

普通分类后，还会按大小阈值、已知分片模式和重复地址过滤。通过 `resourceManager.addResource → notifyResourceFound` 即时加入对应标签页的资源列表，不需要先按播放器下载按钮。

### 站点规则很重要

| 场景 | 本包的实际处理 | 能力边界 |
| --- | --- | --- |
| 抖音 / TikTok | 匹配 `douyinvod.com`、`douyin.com` 等域名，再结合 `mime_type=video/audio` 等标记和通用 MIME 分类 | 主要是实际网络资源分类；本包未发现像工具箱当前方案那样的抖音播放器 ID 与接口媒体逐项绑定 |
| B 站 | 匹配 B 站及相关 CDN；识别 `.m4s`，根据部分音轨编号或 `type=audio` 区分音视频，结合 MIME 归一化扩展名 | 这是音轨／视频轨发现，不代表已经正确配对或合成为带声音的视频；未知编号仍可能分类不准确 |
| HLS | 解析 M3U8 主清单、清晰度子清单、音轨、初始化片段和媒体分片 | 清单可见不等于一定可访问全部分片 |
| DASH | 解析 MPD、视频／音频表示、初始化段、分片与字节范围 | 单独一个 `.m4s` 不能证明是完整视频 |
| YouTube | 独立 MAIN-world 脚本按当前视频 ID 请求播放器信息，整理 formats、adaptiveFormats 和字幕 | 专用接口可能变化；静态代码接通不等于当前所有视频都能成功 |

YouTube 消息链为：注入脚本 `postMessage` → 内容脚本 `Xo` 添加／识别 `SNAPWC_` 前缀 → `fu/q0` 的 `SITE_RESOURCES_DETECTED` → 背景脚本 `registerDetectedResources` → 同一资源列表。

B 站规则也不是无条件放行所有 `.m4s`：通用过滤器仍排除扩展名为 `.m4s` 的条目，只有经过 MIME／站点规则等归一化的资源才可能进入列表。将扩展名标为 `.mp4` 本身并没有进行封装转换。

## 3. 下载时做了什么

### 普通文件

`content-script.js` 的 `du` 下载处理器经 `S0 → w0 → I0` 选择：

- 单请求流式读取：`R0`；
- 服务器支持 Range 且大小满足条件时，默认 5 个并发任务：`x0`；
- 最后创建 Blob，并用浏览器下载链接保存文件。

背景脚本 `Vi` 用 `declarativeNetRequest` 设置会话规则，复用部分原请求头，包括来源相关信息，并调整相关响应头。这能解释为什么“浏览器里能用的地址”直接复制到其他下载器后不一定还能下载。

借鉴时应限制头信息的作用域、生命周期和目标域名；不要跨站复制 Cookie，也不要把凭据写入导出的 TXT。

### HLS / DASH 点播：分片下载不等于音视频合并

`S0 → L0 → Hf` 会分别处理 `streamVideoSegments` 与 `streamAudioSegments`。各自下载分片后，使用 `new Blob(segmentBuffers)` 拼接，并分别保存文件。

这条浏览器下载路径没有把独立视频轨与音频轨混流成单个文件。本包没有发现 FFmpeg 可执行文件或 FFmpeg WASM 引擎。虽然包含 hls.js、dash.js、mpegts.js 等播放依赖，但这不能证明下载出口执行了通用 MP4 转换。

特别是 `Hf` 固定使用 `.mp4` 后缀；对某些 TS 分片，拼接后的实际媒体仍可能是 MPEG-TS。后缀变更不等于转封装。不能把它作为工具箱“输出常见、完整、带声音 MP4”的实现标准。

### 录制与加密边界

直播和部分被标为特殊加密的点播，会进入 `U0 / Wf`，建立隐藏播放器，尝试通过 `captureStream / MediaRecorder` 录制。

这不是原始文件高速下载，通常受播放时长、浏览器编码支持及录制限制影响。代码中有 DRM 分支，并不能证明它可以绕过 DRM；受保护内容可能无法播放或捕获。本次没有运行、验证这种能力，也不建议工具箱以此承诺 DRM 下载。

### 静态检查发现的完整性风险

- `D0` 的单片下载失败被记录为 `null`；上层 `Hf` 过滤空片后仍有报告完成的路径，可能留下缺片文件。
- 普通 Range 并发路径没有严格验证每段响应与预期范围一致；服务端忽略 Range 时存在重复拼接的风险。

以上是源代码路径风险，不是本次已动态复现的产品故障。工具箱应坚持分片齐全、范围匹配、封装正确、音轨与时长校验后才报告成功。

## 4. 是否需要自己的服务器

这种“在用户浏览器捕获地址，在用户电脑下载并合并”的结构，不要求我们自建视频解析服务器。工具箱可以继续使用 WebView2、站点适配器以及本地 yt-dlp / FFmpeg。

但不能把 SnapWC 描述成完全离线：本包有 SnapWC 下载网页集成、版本检查请求，以及受配置控制的本地桌面端桥接。下载入口先尝试桌面端，失败时可以打开 `snapwc.com/bex-download`，该页面再通过内容脚本桥获取资源信息并发起下载。

桌面桥本身连接 `127.0.0.1:29102–29121`；提交内容可包含媒体地址、来源及已捕获请求中的 Cookie 头。它不是读取整个浏览器 Cookie 数据库，但仍涉及会话信息，不能随意照搬。官网动态下发的页面代码和包外桌面端不在本次源码范围内，因此本次不能给出完整的隐私安全保证。

## 5. 对宝哥工具箱现有问题的具体启发

| 问题 | 当前源码依据 | 建议修复 |
| --- | --- | --- |
| 抖音悬浮按钮成功，列表没有对应视频 | `PollPlayers` 只缓存播放器快照；可靠绑定后的命名资源在 `ConfirmPlayerDownload` 中才入列表 | 将可靠绑定结果自动发布到统一资源集合；悬浮按钮、列表共享去重与下载路由，后台识别不自动开始下载 |
| B 站番剧列表无视频 | `WebResourceRules.Classify` 无条件排除 `.m4s`；当前没有音视频轨道分类与配对 | 增加轨道级模型及 B 站适配，不把所有 `.m4s` 当完整视频显示 |
| B 站 blob 播放器按钮拒绝下载 | `PlayerMediaBinding.Resolve` 的 blob 分支只支持抖音 | 识别正在播放的明确单集身份，绑定正确资源；不能拿整个季度 URL 或随便一条 CDN 请求代替当前集 |
| 用户要求下载常见格式且有声音 | 工具箱已有本地 yt-dlp / FFmpeg 下载、合并及检查链 | 复用现有下载后端，补齐识别与绑定；不要以重命名后缀代替转换 |

推荐保留两层概念：底层“发现了请求／轨道”，上层“确认这是当前视频且可以完整下载”。展示可下载视频时要经过上层确认，避免把预加载、广告、单独音轨或半截分片误当成当前视频。

本次仅研究，未修改工具箱生产代码，也未据此重新打包。
